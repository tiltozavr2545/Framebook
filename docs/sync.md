# Синхронизация и бэкап

Как пользовательские данные переезжают между устройствами и как их не
потерять. Сервера нет — роль общего хранилища играет Google Drive самого
пользователя. Что именно синхронизируется — в [data-model.md](data-model.md).

**Статус: проект до Этапа 5.**

---

## Общая схема

- Вход — Google Sign-In, scope только `https://www.googleapis.com/auth/drive.appdata`.
  Приложение видит **только свою скрытую папку** (`appDataFolder`) — ни
  остальной Drive пользователя, ни свои файлы в его интерфейсе. Scope
  относится к нечувствительным (non-sensitive), что упрощает настройку
  OAuth-приложения (см. [operations.md](operations.md)).
- В папке — один файл состояния `framebook-sync.json.gz` и до семи дневных
  копий `framebook-backup-YYYY-MM-DD.json.gz`.
- Каждое устройство хранит **полное** состояние локально и при синхронизации
  сливает его с файлом. Нет журнала операций и нет «главного» устройства.
- Без входа приложение работает целиком, просто на одном устройстве.

---

## Формат файла

JSON, сжатый gzip. Строки — те же колонки, что в БД, в `snake_case`; время —
мс UTC; оценка — `score_half`.

```json
{
  "format_version": 1,
  "written_at": 1760870400000,
  "written_by": "6f1c…-device-uuid",
  "app_version": "0.5.0+5",
  "works": [
    {"work_key": "tmdb:tv:1399", "kind": "tv", "parent_key": null, "tmdb_id": 1399,
     "imdb_id": "tt0944947", "kp_id": 464963, "title": "Игра престолов",
     "original_title": "Game of Thrones", "release_date": "2011-04-17", "year": 2011,
     "poster_path": "/1XS1oqL89opfnbLl8WnZY1O1uJx.jpg", "genre_ids": [10765, 18],
     "snapshot_updated_at": 1760870000000}
  ],
  "ratings": [
    {"work_key": "tmdb:tv:1399", "score_half": 17, "note": "Первые четыре сезона — 9",
     "created_at": 1760000000000, "scored_at": 1760000000000,
     "updated_at": 1760000000000, "updated_by": "6f1c…", "deleted_at": null}
  ],
  "watchlist": []
}
```

Правила формата:

- `format_version` растёт при **любом** изменении состава полей, даже при
  добавлении необязательного. Старый клиент не знает нового поля, и при
  перезаписи файла оно молча пропало бы у всех. Альтернатива — хранить
  незнакомые поля сырым хвостом и возвращать при записи — дороже, а нужна
  только при долгом сосуществовании версий. У одного человека с двумя
  телефонами его нет.
- Клиент, увидевший `format_version` больше поддерживаемого, синхронизацию
  не выполняет и показывает «обновите приложение». Перезаписать файл своим
  представлением он не имеет права.
- Новый клиент читает все прежние версии формата (миграция при чтении) —
  это нужно и для импорта старых экспортов.
- В файл попадают все строки `ratings` и `watchlist`, включая tombstone, и
  те строки `works`, на которые они ссылаются, вместе с предками.
- Ключи API, настройки и кэш рейтингов в файл не попадают никогда.

## Слияние

Каждая строка `ratings` и `watchlist` — это LWW-регистр (last write wins) по
ключу `work_key`. Побеждает версия с большим `(updated_at, updated_by)`:
сначала время, при равенстве — лексикографически больший `device_id`.
Tombstone — обычная версия строки и побеждает или проигрывает по тем же
правилам. Строки `works` сливаются так же, по `snapshot_updated_at`.

Такое слияние **коммутативно, ассоциативно и идемпотентно**: неважно, в каком
порядке и сколько раз устройства синхронизировались — состояния сходятся.
Это свойство — главное, на что опирается остальной алгоритм, и оно покрыто
тестами на случайных последовательностях правок (property-based).

### Алгоритм одного прохода

1. Найти файл: `files.list` в `spaces=appDataFolder` по имени. Если файлов
   с этим именем несколько (два устройства одновременно создали первый
   файл) — слить все, оставить самый старый, остальные удалить.
2. Скачать содержимое (`alt=media`) и запомнить `modifiedTime`.
3. Проверить `format_version`.
4. Слить удалённое состояние с локальным. В локальную БД в **одной
   транзакции** записать строки, где выиграла удалённая версия.
5. Если в слитом состоянии есть строки, где выиграла локальная версия (то
   есть удалённое отличается от слитого), — загрузить слитое состояние.
   Перед загрузкой перечитать метаданные файла: если `modifiedTime`
   изменился после шага 2, вернуться к шагу 2 (не больше трёх попыток).
6. Записать `last_sync_at` и `modifiedTime` в `sync_state`.

Условной записи (If-Match) у загрузки содержимого в Drive API v3 нет, поэтому
между шагами 5 и 6 остаётся окно гонки: другое устройство может перезаписать
файл, не увидев нашей загрузки. Потери данных это не даёт: проигравшее
устройство сохранило свои строки локально, и на следующей синхронизации шаг 5
загрузит их снова. Гонка задерживает изменение, но не теряет его. Это и
есть причина, по которой каждое устройство держит полное состояние.

### Когда синхронизироваться

- при запуске приложения и при возврате в него, если с прошлой
  синхронизации прошло больше 5 минут;
- через 30 секунд после последнего изменения (debounce);
- по кнопке «Синхронизировать» в настройках.

Без сети — тихо откладывается до следующего повода. В фоне (когда
приложение закрыто) в MVP не синхронизируется.

### Часы устройств

`updated_at` берётся с часов устройства. Если часы одного устройства
отстают на час, его правка в течение этого часа проигрывает более ранней
правке с другого. Для одного человека с двумя телефонами это почти не
случается. Защита от худшего случая — монотонность внутри строки: новое
`updated_at = max(now, прежнее updated_at + 1)`, так что правка на
устройстве с отстающими часами хотя бы не проигрывает своей же предыдущей
версии.

### Tombstone

В MVP хранятся вечно. Оценка — это около 300 байт JSON, так что даже
5000 строк с заметками после gzip занимают сотни килобайт. Чистка старых
tombstone возможна только с правилом «устройство, не синхронизировавшееся
дольше N дней, при следующем входе заменяет, а не сливает» — это в
[future-development.md](future-development.md).

## Первый вход и выход

- **Первый вход на устройстве с локальными данными, когда в Drive уже есть
  файл**, — обычное слияние, а не замена. Перед ним — диалог со
  счётчиками: «на устройстве 120 оценок, в Drive 340, после объединения
  будет 395».
- **Выход из Google** — локальные данные остаются, файл в Drive остаётся.
- **«Удалить данные из Google Drive»** — удаляет файл и копии. Другие
  устройства, которые ещё вошли, при следующей синхронизации создадут файл
  заново из своего состояния; это написано в диалоге подтверждения.

## Бэкап

Синхронизация — не бэкап: удаление оценки по ошибке разъедется на все
устройства так же исправно, как и правильное изменение. Поэтому отдельно:

- **Дневные копии в Drive.** Первая синхронизация за сутки, перед
  загрузкой, копирует текущий файл в `framebook-backup-YYYY-MM-DD.json.gz`.
  Хранятся последние 7, старшие удаляются. Восстановление — из списка в
  настройках.
- **Экспорт в файл** — тот же формат, через системный диалог «Поделиться»
  или «Сохранить в…». Работает без входа в Google.
- **Импорт из файла** — по умолчанию **слияние** по тем же правилам. Есть
  вариант «Заменить всё», с подтверждением: всё локальное, чего нет в файле,
  получает tombstone с новым `updated_at`, поэтому замена разъезжается по
  остальным устройствам, а не откатывается ими.
- **Восстановление из дневной копии** — то же, что импорт с заменой.

## Ошибки

| Ситуация | Поведение |
|---|---|
| нет сети | тихо отложить |
| 401 / токен отозван | пометка в настройках «нужно войти снова», без модальных окон |
| квота Drive исчерпана | сообщение в настройках; локальная работа не страдает |
| файл не разбирается (битый JSON, gzip) | не перезаписывать; сообщение и предложение восстановить из дневной копии |
| `format_version` новее | «обновите приложение», синхронизация выключена до обновления |

Последняя ошибка хранится в `sync_state.last_sync_error` и видна в
настройках вместе со временем последней успешной синхронизации.
